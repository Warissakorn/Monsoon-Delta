# การบันทึกและโหลดรอบเล่น

เอกสารนี้อธิบาย API และรูปแบบเซฟที่ใช้งานอยู่ ดู [สถานะและผลตรวจล่าสุด](../STATUS.md) สำหรับขอบเขตระบบโดยรวม

เพิ่ม `core/save_io.gd` ตาม S-04 ของสเปก 02 และเชื่อมกับ `GameSession`, เมนู Continue และหน้าจอเกมแล้ว F5 เปิดเมนูหลัก ส่วนห้องทดลองน้ำเปิดแยกและไม่บันทึกทับรอบปกติ

## API

```gdscript
var error := SaveIO.save(state)  # user://save.json
if error.is_empty():
    var loaded := SaveIO.load_game()
    if loaded["state"] != null:
        state = loaded["state"]
```

ทุกเมธอดรับ path เป็น argument สุดท้ายเพื่อแยกเซฟทดสอบออกจากรอบเล่นจริง:

| เมธอด | ผลลัพธ์ |
|---|---|
| `save(state, path)` | `""` เมื่อสำเร็จ, `msg.save_failed` หรือ `msg.save_unsupported` เมื่อ ruleset ไม่รองรับ |
| `load_game(path)` | `{state: GameState หรือ null, error: String}` |
| `has_save(path)` | ตรวจว่ามีไฟล์โดยไม่อ่าน แก้ หรือลบไฟล์ |
| `delete_save(path)` | `""` เมื่อสำเร็จ/ไม่มีไฟล์ หรือ `msg.save_failed` |

โหลด path ที่ไม่มีไฟล์คืน state เป็น null และ error ว่าง ไฟล์ที่อ่านได้แต่ผิดรูปแบบคืน `msg.save_corrupt` และพยายามลบตาม S-04 ส่วนความผิดพลาดในการเปิด/อ่านไฟล์คืน `msg.save_failed` โดยเก็บไฟล์ไว้ `has_save` จึงไม่ได้ยืนยันว่าโหลดได้ เมนู Continue ต้องตรวจผล `load_game` อีกครั้ง

เมื่อไฟล์ผ่านการอ่าน/แปลง JSON และตรวจ `format`/หมายเลขเวอร์ชันแล้ว envelope ที่ใหม่กว่า v5 คืน `msg.save_unsupported` โดยไม่ลบไฟล์ เช่นเดียวกับ envelope ที่รองรับแต่มี `state.ruleset` เป็นสตริงชื่อที่ไม่รู้จัก การตรวจนี้มาก่อน validation ของ payload เพื่อไม่ตีความข้อมูลจากรุ่นใหม่ว่าเสีย ข้อมูลผิดรูปแบบของรุ่นที่รู้จักยังใช้นโยบาย `msg.save_corrupt` เดิม

การบันทึกเขียนไฟล์ `.tmp` ใน directory เดียวกัน ตรวจข้อผิดพลาด แล้ว rename ทับปลายทาง ถ้าเขียนหรือแทนที่ไม่สำเร็จจะคืน error และรักษาเซฟเดิมไว้ ไม่ลบเซฟเดิมก่อนเขียน เซฟบทสอนเล่นไม่เขียนทับหรือลบเซฟปกติ ส่วน GAME_OVER ของ ruleset ที่รองรับลบเซฟตาม S-04; ruleset ที่ไม่รู้จักคืน `msg.save_unsupported` ก่อนเขียนหรือลบไฟล์

## ขอบเขตข้อมูล

รองรับรอบเล่นที่ราบลุ่มแบบ 5 หรือ 10 ปี เป้าหมายหมู่บ้าน ผู้นำที่มีใน balance, difficulty 0–10 และ phase PLANNING/HARVEST ที่ระบบเกมใช้งานจริง เซฟ HARVEST เก็บรายงานและผลแพ้/ชนะไว้ โหลดแล้วรอ `GameFlow.continue_after_harvest` ตามเดิม ไม่เรียกเก็บเกี่ยวหรือเริ่มปีซ้ำ การ์ด เหตุการณ์ และแผนที่อื่นยังไม่รองรับ

ตรวจชนิดและช่วงค่าก่อนเรียก `GameState.from_dict`: ฟิลด์ที่จำเป็น, enum, 61 ช่องตามลำดับ hex, ทรัพยากร, ฝน, พยากรณ์, รายงานเก็บเกี่ยว และ modifier ที่รู้จัก seed กับสถานะ RNG ใช้สตริงจำนวนเต็ม signed 64 บิต ไม่ผ่านตัวเลข JSON ประวัติ undo/redo และ cache ไม่ถูกบันทึก; โหลดแล้วสร้าง index/mods ใหม่และเริ่มประวัติทั้งสองว่าง

จำกัดไฟล์ 1 MiB, ค่าจำนวนเต็มทั่วไปไม่เกิน `2^53−1` และ `water_iterations` ที่ได้หลังใช้ modifier ต้องเป็นจำนวนเต็ม 1–1000 เพื่อจำกัดงานจากไฟล์เซฟ ตรวจ UTF-8 ก่อนแปลงข้อความ เพื่อให้ไฟล์เสียคืน error ที่คาดไว้โดยไม่เกิด script error

รูปแบบเซฟเป็น envelope `{format: "monsoon_save", version: 1, 2, 3, 4 หรือ 5, state: {...}, float64: {...}}` โดยเลือกเวอร์ชันตามข้อมูลด้านล่าง ส่วน `state.version` ภายในยังเป็น 1 ทุกแบบ ข้อมูลบิต float64 ประกอบรักษาค่าน้ำ ฝน พยากรณ์ และ modifier ให้ตรงเดิม Godot 4.6.3 อ่านตัวเลข JSON บางค่ากลับมาไม่ตรงบิต แม้เขียนด้วย `full_precision=true` เช่น `0.013960820753117553` จึงต้องเก็บความละเอียดเพิ่ม การอ่านบิตใช้ข้อมูลตัวเลขเท่านั้น ไม่ deserialize object จากไฟล์

รอบกฎเดิม (`legacy`) ที่ไม่มีประวัติภาพหมู่บ้านยังเขียน envelope v1 เมื่อเป็น classic/none หรือ v2 เมื่อเป็นรอบ 10 ปีหรือเลือกเป้าหมาย โดย v2 ต้องมี `run_mode`, `village_goal`, `goal_achieved_year` ครบทั้งสามฟิลด์ โหลด v1 ที่ไม่มีฟิลด์เหล่านี้เป็น classic/none/0; ไม่ยอมรับฟิลด์มาไม่ครบหรือ v1 ที่แอบกำหนดโหมดยาว ตรวจปีและผลชนะเทียบระยะเวลาของโหมด เหรียญเป้าหมายคงอยู่เมื่อโหลดและขึ้นปีใหม่ ทุกเวอร์ชันใช้ข้อมูล float64 เดิมเพื่อรักษาฝนและ RNG

ฟิลด์ `float64` ที่จำเป็นเก็บ `forecast_min`, `forecast_max`, `rain_inflows`, `tile_water` และ `year_mod_values` เป็นสตริง hex 16 ตัวต่อค่า (8 ไบต์จาก `encode_double`) ตรวจจำนวนรายการ ความเป็นค่าจำกัด และความสอดคล้องกับตัวเลข JSON ก่อนใช้บิตจริง ไม่รับเซฟที่ขาดข้อมูลประกอบนี้ ค่าต้นทุนต้องไม่ล้นขอบเขต `Vector2i` และ modifier ทางกายภาพที่มีผลทำให้น้ำหรืออาหารติดลบจะถูกปฏิเสธ

## v3: ประวัติภาพหมู่บ้านและอายุอาคาร

เกมใหม่และการเริ่มรอบใหม่ผ่าน `Boot._start_game` เปิด `living_village=true` แล้วใช้ envelope v3 ทั้ง classic และ long เมื่อใช้กฎเดิม โดยเก็บฟิลด์โหมด/เป้าหมายครบสามตัว พร้อม `state.settlement_progress`; ถ้าเลือก `bracing_v1` ใช้ v4 หรือเปิดความชื้นในนาใช้ v5 แทน การเรียก `GameFlow.new_game` หรือ `GameSession.start` โดยตรงยังปิดค่าเริ่มต้นประวัติภาพนี้ เพื่อให้บอท fixture และผู้ใช้ API เดิมได้ state เดิม ผู้เรียกที่ต้องการประวัติภาพต้องส่ง flag นี้อย่างชัดเจน ส่วน Continue โหลดข้อมูลเดิมโดยไม่เพิ่มประวัติ ไม่เขียนไฟล์ซ้ำ และไม่อัปเกรดกติกากลางรอบ

`settlement_progress` เป็น dictionary ตามตารางนี้; เมื่อไม่ได้เปิดใช้ ค่าในหน่วยความจำเป็น `{}` และ `GameState.to_dict()` จะละฟิลด์นี้ออกทั้งหมด:

| ฟิลด์ | ข้อมูล |
|---|---|
| `version` | เวอร์ชัน metadata ปัจจุบันเท่ากับ 1 แยกจาก envelope และ `state.version` |
| `condition` | `struggling`, `stable` หรือ `thriving`; เริ่ม `stable` |
| `evaluated_year` | ปีล่าสุดที่ประเมินหลังเก็บเกี่ยว; เริ่ม 0 ป้องกันประเมินปีเดียวซ้ำ |
| `candidate`, `candidate_years` | สภาพที่กำลังรอยืนยันและจำนวนปีต่อเนื่อง 0–1; เมื่อครบสองปีจะเปลี่ยนสภาพหนึ่งระดับแล้วรีเซ็ต |
| `buildings` | dictionary คีย์พิกัด `"q,r"` สำหรับสิ่งก่อสร้างทุกหลังที่ยังอยู่ แต่ละรายการมี `building` ชื่อ enum, `built_year`, `built_turn` และ `stage` 0–2 |

ประเมินสภาพหลังการเก็บเกี่ยวจริง: คนย้ายเพราะหิว/บ้านไม่พอ อาหารหมด หรือประชากรหมดให้เป้าสภาพ `struggling`; อาหารคงเหลือพอเลี้ยงประชากรหนึ่งปี ไม้พอสร้างบ้านธรรมดาสองหลัง และบ้านพอให้เป้า `thriving`; กรณีอื่นให้ `stable` ต้องได้เป้าเดียวกันสองครั้งต่อเนื่องจึงขยับสภาพหนึ่งระดับ อายุอาคารเท่ากับปีปัจจุบันลบปีสร้าง เมื่อ `thriving` อาคารอายุอย่างน้อยหนึ่งปีพัฒนา `stage` ได้ปีละหนึ่งขั้นสูงสุด 2; เมื่อ `struggling` ลดปีละหนึ่งขั้นต่ำสุด 0; `stable` คงขั้นเดิม ข้อมูลเหล่านี้เปลี่ยนภาพตกแต่งเท่านั้น ไม่เปลี่ยนผลผลิต ทรัพยากร ความจุบ้าน ความทนน้ำ คะแนน หรือ RNG

การสร้างสำเร็จบันทึกปี/เทิร์นและเริ่มขั้น 0; การรื้อหรือพังลบประวัติของหลังนั้น การสร้างชนิดเดิมบนช่องเดิมเริ่มอายุใหม่ สำเนา พรีวิว และ Undo/Redo เก็บ metadata ครบตาม snapshot โดยไม่ทำให้เวลาจริงเดินเพิ่ม

validator ของ v3 ตรวจ schema metadata และรายการอาคารแบบครบฟิลด์ ไม่รับฟิลด์เกิน ค่า condition/candidate ต้องรู้จักและสอดคล้องกับตัวนับ ปี/เทิร์นสร้างต้องไม่อยู่ในอนาคต ขั้นพัฒนาต้องเป็นจำนวนเต็มไม่เกิน 2 และไม่เกินอายุ รายการต้องตรงชนิดและพิกัดของสิ่งก่อสร้างที่ยังอยู่ครบทุกหลัง ไม่มีรายการหลงเหลือหรือพิกัดนอกแผนที่ v1/v2 ที่แนบ metadata นี้และ v3 ที่ไม่มี metadata/ฟิลด์โหมดครบจะถูกปฏิเสธ ไม่เดาประวัติย้อนหลังให้เซฟเก่า

หมายเลข v3 นี้รองรับประวัติภาพหมู่บ้านเท่านั้น ชื่อ “เซฟ v3” ใน [แบบเสนอการ์ด M5](../design/CARD_CATALOG.md) เคยใช้กับแนวคิด ruleset/catalog และ `actual_paid_wood` ซึ่งยังไม่ถูกพัฒนา แบบนั้นต้องกำหนดเวอร์ชันใหม่และสัญญาย้ายข้อมูลก่อนเริ่มใช้ ไม่ถือว่า envelope v3 ปัจจุบันเปิดใช้การ์ด เหตุการณ์ หรือสูตรคืนไม้ใหม่แล้ว

## v4: กติกาค้ำบ้านที่เลือกตอนเริ่มรอบ

[ค้ำบ้านฉุกเฉิน](../features/HOUSE_BRACING.md) เปิดด้วย `ruleset = "bracing_v1"` ตอนสร้างรอบและใช้ envelope v4 ทั้ง classic/long ไม่ว่าจะเปิดประวัติภาพหมู่บ้านหรือไม่ ต้องมี `state.ruleset` ตรงค่านี้และฟิลด์ `run_mode`, `village_goal`, `goal_achieved_year` ครบ ส่วน `settlement_progress` ไม่บังคับ แต่เมื่อมีต้องผ่าน validator เดิมของประวัติภาพ

ทุกช่องใน v4 ต้องมี `brace_turns` เป็นค่าจำนวนเต็ม 0 หรือ 1 รวมถึงช่องที่ไม่มีบ้าน ค่า 1 อนุญาตเฉพาะ phase `planning` และ building `house`/`stilt_house`; HARVEST ต้องเป็น 0 ทุกช่อง การตรวจจำนวนเต็มยอมรับตัวเลข JSON ที่มีค่าเต็ม เช่น `1.0` แต่ปฏิเสธเศษส่วน สตริง และ boolean ตรวจเงื่อนไขเดียวกันก่อนบันทึกเพื่อไม่สร้างไฟล์ที่โหลดกลับไม่ได้

รอบ legacy ละทั้ง `ruleset` และ `brace_turns` จากข้อมูลที่บันทึกและ snapshot; โหลดกลับเป็น `legacy`/0 โดยไม่เปิดกฎใหม่ เซฟ v1–v3 ที่แนบฟิลด์เหล่านี้และ v4 ที่ขาดฟิลด์ที่จำเป็นหรือใช้กติกาผิดรุ่นถือว่าผิดรูปแบบ ยกเว้นชื่อ ruleset ที่ไม่รู้จักซึ่งคืน unsupported และเก็บไฟล์ไว้ตามข้างต้น รูปแบบ v1/v2/v3 เดิมยังคงเดิม ไม่อัปเกรดรุ่นเพียงเพราะเปิดเกมด้วยค่าตั้งใหม่

สำเนา พรีวิว และ Undo/Redo ของ `bracing_v1` เก็บ ruleset/สถานะค้ำครบ โหลดบ้านที่ค้ำไว้แล้วไม่หักต้นทุนซ้ำหรือหมดอายุก่อนเวลา ค้ำหมดอายุหลัง resolver จบหนึ่งเทิร์น รวมถึงเทิร์นแห้งหรือแพ้; พรีวิวทำบนสำเนาเท่านั้น ผลค้ำอยู่ในรายงานเทิร์นชั่วคราว ไม่ใช่ข้อมูล checkpoint เพิ่มเติม

## v5: ความชื้นสะสมในนา

[ความชื้นสะสมในนา](../features/SOIL_MOISTURE.md) ใช้ envelope v5 ทั้ง classic/long เมื่อเลือก `moisture_v1` หรือ `bracing_moisture_v1` ตอนเริ่มรอบ ฟิลด์โหมด/เป้าหมายครบสามตัวตาม v4 และรองรับ `settlement_progress` ที่ผ่าน validator เดิมได้ แต่ไม่บังคับให้มี

ทุกช่องต้องมี `soil_moisture` เป็นค่าจำนวนเต็ม 0–2; ช่องที่ไม่ใช่ `paddy` หรือนาที่ `paddy_dead` ต้องเป็น 0 ไม่ยอมรับฟิลด์หาย เศษส่วน สตริง หรือ boolean `moisture_v1` ละ `brace_turns` ทั้งหมด ส่วน `bracing_moisture_v1` ต้องมีและตรวจค้ำแบบ v4 ทุกช่อง ค้ำและความชื้นเป็นสถานะอิสระ ไม่เติมค่าให้ข้อมูล v5 ที่ขาดฟิลด์

เซฟ v1–v4 ไม่รับ `soil_moisture` แม้เป็น 0 และไม่อัปเกรดกฎเมื่อโหลด ค่านอกกฎในหน่วยความจำถูกปฏิเสธก่อนบันทึก เช่น ความชื้นที่ไม่ใช่ 0 ในรอบที่ไม่ได้เปิดใช้ ความชื้นข้ามเก็บเกี่ยว/ขึ้นปีใหม่ได้ แต่การตายหรือรื้อนาล้างเป็น 0 พรีวิวและ Undo/Redo รักษาค่าตาม snapshot ไม่ใช้ RNG เพิ่มและไม่เปลี่ยนปริมาตรน้ำ

ชุด `settlement_progress` ตรวจสภาพรายปี อายุ/ขั้นอาคาร สร้างใหม่หลังรื้อ ความเสียหาย Undo/Redo พรีวิว กฎเกมเดิม ความเข้ากันได้ของ v1/v2, v3 ที่ผิดรูปแบบ และบันทึก–โหลดทุกเทิร์น/เก็บเกี่ยวในรอบที่เปิดประวัติภาพ โดยเทียบ float64/RNG และ metadata แบบตรงค่า

ชุด `bracing_save` ตรวจ v4 ที่มี/ไม่มีประวัติภาพ การโหลดค้ำค้างแล้วจบเทิร์น ฟิลด์ค้ำขาด/ผิดชนิด/ผิดช่วงหรืออยู่ผิด phase/อาคาร การแนบกฎใหม่ใน schema เก่า การรักษาไฟล์ของ envelope/ruleset รุ่นที่ไม่รองรับ การเขียนล้มเหลว และการบันทึก v1/v2/v3 กลับโดยรักษา bytes เดิม ดูผลตรวจรอบล่าสุดใน STATUS

ผลตรวจฐาน SaveIO เมื่อ 2026-10-16 บน Godot 4.6.3: เทสต์บันทึก–โหลด 18 รายการและชุดรวม ณ เวลานั้น 125 รายการผ่านทั้งหมด; import และ headless sandbox smoke ผ่าน การรองรับเซฟโหมดยาวและเป้าหมายเพิ่มภายหลัง ดู [ผลตรวจโหมดระยะยาว](../features/LONG_RUNS.md#ผลตรวจ) และ [ผลตรวจล่าสุด](../STATUS.md)

`GameSession` บันทึกหลังเริ่มเกม คำสั่งสำเร็จ undo/redo จบเทิร์น และ continue หลังเก็บเกี่ยว ส่วน GameFlow ยังคงไม่มี I/O เพื่อให้บอท/preview/sandbox ไม่แตะเซฟปกติ หน้าจอเกมแสดงข้อความเมื่อเซฟล้มเหลวและให้ลองใหม่ก่อนกลับเมนูหรือปิดหน้าต่าง ดู [หน้าจอเกม M4](../features/M4_PLAYABLE.md)

`GameSession.turn_history()` คืนสำเนาประวัติผลจริงเฉพาะช่วงเล่นครั้งปัจจุบัน เรียงเก่าไปใหม่ สูงสุด 30/60 เทิร์นตามโหมด เก็บปี/เทิร์นก่อนเลื่อนเวลา รายงานน้ำ/ความเสียหาย/ผลผลิตแบบย่อ ผลเก็บเกี่ยวเฉพาะเทิร์นสุดท้าย และ outcome หลังเก็บเกี่ยว ประวัติอยู่นอก GameState และเริ่มว่างเมื่อเริ่มหรือโหลดเกมสำเร็จ การดูประวัติไม่บันทึกไฟล์; เมื่อจบเทิร์นแล้วเขียนเซฟล้มเหลว ผลจริงยังอยู่ในประวัติให้ดูและลองบันทึกซ้ำได้

เมื่อมีค้ำถูก resolve รายงานแบบย่อเพิ่ม `brace_results` พร้อม `coord` (`Vector2i`), `base_threshold`, `protected_threshold`, `level`, `prevented_loss` และ `expired` เพื่อแยกค้ำช่วยให้รอด ค้ำหมดอายุเฉย ๆ และน้ำเกินเกณฑ์ที่ค้ำรับได้ ข้อมูลนี้สร้างแม้ปิดการบันทึกภาพของ resolver และคงผลไว้หลังล้าง `brace_turns` แล้ว `TurnReport.to_dict()` แปลงพิกัดเป็น `[q, r]`; ทั้งรายงานแบบ dict และประวัติละคีย์นี้เมื่อไม่มีผลค้ำ ประวัติเหล่านี้ไม่ลงเซฟและหายเมื่อเริ่ม/โหลด session ใหม่

รอบที่เปิดความชื้นเพิ่ม `moisture_changes` ในรายงานเทิร์นและประวัติแบบย่อ: `coord`, `before`, `after`, `yield_from_moisture` (0 หรือ 1) มีหนึ่งรายการต่อแปลงนาระหว่าง resolve รวมกรณีค่าไม่เปลี่ยน/นาตาย/แพ้ศาลา สร้างแม้ปิดภาพและไม่ลง checkpoint; `TurnReport.to_dict()` แปลงพิกัดเป็น `[q, r]` และละคีย์เมื่อไม่มีรายการ เพื่อรักษารายงานกฎเดิม

`GameSession.last_harvest_food_by_tile` เป็นข้อมูลชั่วคราวพิกัด → อาหารข้าวที่เก็บเกี่ยวได้จริง ใช้แสดงคนขนข้าวโดยอาศัย `Harvest.paddy_food_by_tile` ซึ่งเป็นสูตรเดียวกับการคิดอาหาร ล้างเมื่อเริ่ม/โหลดเกมหรือเรียกจบเทิร์นครั้งถัดไป ไม่อยู่ใน state เซฟ หรือประวัติผลแบบย่อ การอ่านข้อมูลนี้ไม่สร้างผลผลิตซ้ำ เช่นเดียวกับทิศน้ำและผลผลิตไซรายช่องใน `TurnReport` ที่ใช้เพื่อภาพเท่านั้น
